## 0. 목적·규칙

- **질문**: RIO가 제공하는 능력을 우리 코드가 ①쓰는가 ②안 쓰면 무엇이 막는가.
- **판정 5값**: `활용중 ✅` / `불가(RIO 제약)` / `구조가 막음` / `의도보류` / `관측대기`
- **규칙**: 읽기 전용(코드 수정·빌드·실측 없음). 모든 판정에 file:line 근거. 실측 없인 못 가리는 행은 **관측대기** 표시만 하고 계측 설계는 별도 작업(실측 플랜)으로 넘김. RIO API 의미론이 불확실한 행은 단정 대신 **[문서 확인 필요]** 표시.
- **결함 사냥 아님**: IOCP 결함 감사는 종료 상태(Docs/IOCP_AUDIT_CLOSED.md) 유지. 공통·IOCP 코드는 결합 확인 목적으로만 읽는다.

## 3. P2~P4 — 대조 읽기 결과

### P2 — Transport_Rio.cpp(689줄) + RioApi.h(107줄) 정독 결과

#### 축1 제출

- **S1 플래그**: RIOReceive·RIOSend 모두 플래그 `0`(즉시 킥) — Transport_Rio.cpp:616, :672. DEFER/COMMIT_ONLY 미사용. 단 **의도보류가 기록으로 남아 있음** — 랩 분할 카운터 주석 ":645-647 이 빈도가 낮으면 배치 제출(RIO_MSG_DEFER)을 넣을 값어치가 없다는 근거가 된다" = ④-b 보류 결정과 일치. 스모크 실측(CC2000)에선 깊이 D4가 랩 왕복을 완전 흡수(followup 0). → **의도보류** (천장급 재확인은 실측 영역)
- **S2 요청당 버퍼 1개**: 코드가 전제로 삼음(:631 "RIO는 요청당 버퍼가 1개다", :568 동일) — 직선 구간만 제출, 꼬리는 완료 후 재제출. 호출은 전부 `&buf, 1`(:616, :672). → **불가(RIO 제약)** [문서 확인 필요: DataBufferCount>1 허용 여부 — Win8 문서 기준 1 고정으로 기억하나 재확인 가치]. 완화 레버 = 링 크기(R4)·랩 DEFER 2요청(S1)
- **S3 제출 비용 모델**: enqueue는 유저모드 링. 플래그 0의 "즉시 킥"에 커널 진입이 붙는지는 **[문서 확인 필요]** — 프로젝트 기존 결론("RIOSend는 syscall 아님", 노션 TODO 기록)과 정합 여부. 어느 쪽이든 **수거(GQCS) syscall 제거는 실측 확정**(worker_kernel 감소)
- **S4 recv 제출**: PostRecv가 recvQ의 **빈 직선 구간 전체**를 제출(:583-584 GetWritePtr+GetDirectWriteSize) — 고정 소버퍼가 아니라 완료 1회에 여러 패킷이 자연 배칭됨. 좋은 구조 ✅

#### 축2 완료

- **C1 배치 수거**: RIODequeueCompletion 상한 256(:23, :435). **실효 배치율 계측이 이미 붙어 있음** — AddDequeue(:448)·AddCompletion(:476), 주석 ":445 IOCP 팔과 같은 잣대". 메모리의 "계측 부착 필요"는 옛 정보 — **부착 완료, 실행만 안 된 상태**. ⚠ 판독 주의: **빈 조회(n=0)도 호출로 센다**(:446) + 유휴 사이클마다 드레인 2회(:543, :558) → RIO의 completions_per_dequeue는 저부하에서 ~3배 희석. IOCP(GQCSEx 블로킹 호출)와 직접 비교 시 이 희석 감안 필수
- **C2 통지 모드**: RIO_EVENT_COMPLETION + NotifyReset(:103-106) — 이벤트 고정, IOCP 모드 미사용. 전환 시 명령 핸드오프(mutex+SetEvent)를 PQCS로 통합 가능(성능+결합 동시) → **미구현·관측대기** (무장+wake 실비용 미측정)
- **C3 무장 배치**: RIONotify는 **유휴 진입 시에만** 무장(:557), 무장 후 재드레인으로 틈새 완료 회수(:558), 바쁠 땐 didWork continue로 무장 생략(:549-550) → 무장 비용 최소화 구조 ✅. wake 빈도 자체는 관측대기 (기존 카운터로 근사 가능: 유휴 패턴에서 dequeue 호출 ≈ wake당 3회)
- **C4 스핀**: 없음 — 주석 ":483 v1은 스핀 없이... 실측 후 필요 시 추가" → **의도보류 유지**

#### 축3 자원

2. **setsockopt 3종 확정** (SetSocketOptions :293-314, accept 소켓에 양팔 공통 적용):
   - SO_LINGER = RST 즉시 종료(:295-299)
   - **TCP_NODELAY 주석 처리 = Nagle 켜진 상태**(:301-303). 코얼레싱 송신이 대부분 MSS급 이상이라 실전 영향은 낮을 것으로 보이나 **미측정** — 소량 꼬리 send에서 지연 후보. 양팔 공통이라 A/B 비교는 공정 → **관측대기(낮은 우선순위)**
   - **SO_SNDBUF는 기본 빌드에서 안 건드림** — `USE_ZERO_SNDBUF=0`(BuildConfig.h:27)이라 :308-309 미컴파일 → OS 기본+자동조정 유지. RIO 함의: SNDBUF>0이면 send 완료=커널 버퍼로 복사 완료(빠른 슬롯 회수)로 해석됨 **[문서 확인 필요]** — D=1이 견디는 이유 후보
   - **SO_RCVBUF는 어디서도 안 건드림** → 커널 수신버퍼 유지. **recv 깊이 1이 치명적이지 않은 이유가 이것** — 재게시 공백 동안 커널 버퍼가 흡수해 TCP 윈도가 즉시 안 선다. ⚠ **결합 함정 기록**: RIO 표준 권고대로 RCVBUF=0을 넣으면(복사 절감) 깊이 1과 조합돼 공백마다 윈도 스톨 — **두 설정은 같이 움직여야 한다**. 메모리의 "RIO는 소켓 수신버퍼를 안 써"는 우리 구성엔 부정확(안 끈 상태)
3. **recv 재게시 지점 확정**: ProcessRecv = MoveWritePtr → **ParsePackets 전체 완료 후** → PostRecv(:485-493). 재게시 공백 = 파싱 시간. 게임 모드는 패킷당 memcpy+큐 push라 짧고, 에코 모드는 파싱 루프 안에서 송신까지 해 공백이 김(게임 부하 판정엔 무영향). recv 링은 CRingBufferST(무락, :109 "한 스레드에서만") — 소유 워커 단독 접근 불변식과 정합 ✅
4. **PostSend 링 락 구간 확정**: 제출 1건당 CRingBufferMT(std::mutex) 획득 — GetSubmitInfo(:766) + MarkSubmitted(Transport_Rio.cpp:657) + 루프 종료 재확인 GetSubmitInfo = 3회, 완료 쪽 ConsumeSubmitted(:715) + GetUnsubmittedSize(:681) = 2회 → **송신 왕복당 링 락 ~5회**. M1의 "제출당 4회" 추정과 부합
5. **RioOwnerIndex 정의 확정**: `ExtractUniqueId(sessionId) % _rioWorkerCount`(IOCPServer.h:487-490) — 48비트 단조 카운터 나머지라 접속 순 라운드로빈 분배. 세션 수 기준 균등, **부하 기준 쏠림은 별개**(핫 세션 몰림) → 관측대기(워커별 카운터 기존)
6. **MAX_SEND_WORKERS = 16**(MonitorManager.h:279) → RioWorkers 상한 16. **실질 제약 아님**(물리 코어 6~10이 먼저 묶고, U커브 바닥이 N4) — P2 발견 N1은 정보성으로 격하

#### 추가 확인 (판정표 재료)

- **RIO 팔의 PostSend 호출자는 전부 소유 워커** — FlushSend 명령(워커)·완료 이어보내기(워커)·Immediate(비소유는 핸드오프 변환, Transport_Rio.cpp:230-241) → `_sendSubmitBusy` 게이트가 RIO에서 구조적으로 무경합(M1의 "RIO send_contention 0"과 정합). 게이트 원자연산은 남지만 무경합 InterlockedExchange라 비용 미미
- **U1 결합의 실체 확정**: 같은 세션 `_sendQ`(CRingBufferMT) mutex를 게임스레드(Enqueue — RequestSendMsg:886/RequestSendRaw:935)와 소유 워커(GetSubmitInfo/MarkSubmitted/ConsumeSubmitted)가 공유. 단 **시간대가 갈린다** — 게임스레드는 틱 중 적재 후 FlushPendingSends로 넘기고, 워커 제출은 그 뒤. 겹침은 "직전 틱 제출의 완료 처리"와 "이번 틱 적재"뿐 → 경합 규모는 관측대기(M1도 배제 증거만)
- **셧다운 대기 구조**: 세션별 IOCount==0을 Sleep(1) 순회 대기(:355-366) 후 TransportStopAfterDrain. RIO×게임부하 90초 행(기존 문제·관측대기)의 무대이나 원인 규명은 이 감사 범위 밖 — 구조 위치만 기록
- **RingBuffer 3포인터**: read ≤ submit ≤ write(:454-456), 미사용자에겐 submitPos=0 무영향(:455) — 부하클라 호환 설계 확인 ✅. RewindSubmitted는 in-flight 0 전제 주석(:438-439) — D=1 부분송신 복구 전용과 정합
- **송신 깊이 2^n 강제**: Start()가 INI 값을 아래 거듭제곱으로 내림(:136-151), `_sendDepthMask` 비트마스크 인덱싱(:412-415) — wrap 안전 ✅
