> 앞 편들 요약: 세션은 배열로 관리하고 SessionID의 세대 번호로 ABA를 가려낸다(1장). IOCount는 CAS로만 올려 좀비 참조를 막고, IO 제출 직후 재확인으로 취소를 놓친 IO를 회수한다(2a장). 이 편은 **세션을 실제로 끊을 때 소켓을 어떻게 닫는가**를 다룬다.

> [그림: deck_08_rst]

주의* 이 서버는 일반 `accept`를 쓰고, 리슨 소켓에는 LINGER를 걸지 않는다. AcceptEx + `SO_UPDATE_ACCEPT_CONTEXT` 사용 시 MSDN은 "inherits the properties of the listen socket"이라고 명시하므로 SO_LINGER가 상속될 수 있으나, 어느 방식이든 **각 세션 소켓에 명시적으로 개별 설정하는 것이 가장 안전하다.**

조치는 한 줄이다 — accept한 소켓마다 `SO_LINGER`를 켜고 대기 시간을 0으로 준다(`l_onoff=1, l_linger=0`). 이러면 `closesocket`이 정상 종료 절차를 밟지 않고 RST를 보내며 즉시 끝난다.

## 효과 (장점)

| 효과 | 설명 |
| --- | --- |
| **TIME_WAIT 회피** | 서버가 `closesocket`해도 소켓이 2분간 TIME_WAIT에 묶이지 않음. 동접이 많고 연결/해제가 빈번한 게임 서버에서 소켓 리소스 고갈 방지 |
| **즉시 포트 해방** | 해당 4-tuple(src IP/port, dst IP/port)이 즉시 재사용 가능 |
| **Send 버퍼 즉시 폐기** | 커널의 TCP send buffer에 아직 전송되지 않은 데이터가 있어도 기다리지 않고 버림. `closesocket`이 블로킹 없이 즉시 반환 |

## 부작용 (위험)

| 부작용 | 설명 |
| --- | --- |
| **미전송 데이터 유실** | `closesocket` 시점에 커널 send buffer에 남아있던 데이터가 전송되지 않고 폐기됨. 예: "방 퇴장 결과" 패킷을 보내고 직후 연결을 끊으면 클라이언트가 해당 패킷을 못 받을 수 있음 |
| **클라이언트 측 에러** | 클라이언트가 `recv`하던 중 RST를 받으면 "Connection reset by peer" 에러 발생. 정상적인 EOF(graceful close)가 아니므로 클라이언트 측에서 에러로 처리할 수 있음 (협의 필요) |
| **구 패킷 충돌 (이론적)** | TIME_WAIT이 없으므로 같은 4-tuple로 즉시 재접속 시 구 연결의 지연 패킷이 신 연결에 섞일 수 있다는 이론적 부작용. 다만 실제로는 4-tuple 일치 + TCP sequence number가 수신 윈도우 범위 안에 들어와야 하고 + checksum도 통과해야 하며 + 설령 통과하더라도 컨텐츠 레이어에서 패킷 파싱/검증에 걸러지므로 현실적 발생 확률은 0에 수렴. TCP 교과서에서 TIME_WAIT 존재 이유를 설명할 때 나오는 시나리오. |

## 게임 서버에서의 판단

게임 서버에서 RST 종료는 **일반적으로 허용되는 관행.**

1. 게임 서버는 서버 측에서 연결을 끊는 경우가 대부분 **비정상 상황**(핵 감지, 타임아웃, 킥)이므로 잔여 데이터 유실이 허용됨
2. TIME_WAIT 소켓 누적은 대규모 서버에서 실질적 문제를 일으킴 (리소스 차지)
3. 클라이언트는 어차피 서버 연결 끊김 시 재접속 흐름을 갖고 있음
