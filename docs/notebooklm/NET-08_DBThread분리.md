# 08. DB Thread 분리 및 저장 설계

> **서버 메모리 = 진실, DB = 저장소.**
> 데이터가 변경된 유저만(dirty flag) 비동기로 저장하고, 일단 뜬 뒤에는 DB가 죽어도 서버는 멈추지 않는다(부팅 때만 반대 — ⑩).

> [그림: 00_cover]

## 설계 배경

게임 루프는 초당 25틱 — 한 틱에 쓸 수 있는 시간이 40ms다. MySQL 저장은 한 건에 수 ms이고 디스크 사정에 따라 더 튄다. 접속자 수만큼 곱해지니 틱 안에서 감당할 수 없다.

게임은 *무엇을 저장할지*만 큐에 넣고, **별도 워커가 저장**한다. (기존 송신 워커의 생산자-소비자 패턴 재사용) — 저장 주기는 10초(설정값 `SavePeriodSec`). 아래에서 말하는 "다음 주기"는 전부 이 10초를 가리킨다.

> [그림: 01_why_async]

## 구조

> [그림: 02_structure]

게임은 **값 스냅샷**(계정·좌표·맵)을 큐에 넣고, 워커는 큐를 통째로 꺼내 UPSERT(`INSERT … ON DUPLICATE KEY UPDATE`)한다.

**현재 저장 대상은 위치뿐이다** — `characters` 테이블 4컬럼(`account_id`, `x`, `y`, `map_id`). 인벤토리·재화처럼 유실이 치명적인 데이터는 아직 없다. 아래의 "잡만 드롭" 정책이 성립하는 것도 이 범위 덕분이다.

※ `accountId`는 1단계에서 `playerId`를 그대로 쓰는 임시값이다. ⑤의 "같은 유저=같은 워커"는 실계정 연동 시 실제 계정 ID 기준으로 바뀐다.

## 설계 결정

> [그림: 03_failure_policy]

| 결정 | 왜 / 트레이드오프 |
| --- | --- |
| **① 비동기 워커** | 틱이 DB 왕복(수 ms)에 막히면 안 됨 — 게임은 push만 |
| **② dirty 선별 저장** | 안 바뀐 유저 재저장은 낭비 |
| **③ MOVING 또는 dirty 판정** | dirty는 정지·접속·존이동 같은 사건에서만 켜지고 저장하면 꺼진다 → 좌표가 매 틱 바뀌는 이동 중은 "움직이는 중"이라는 상태값으로 따로 잡음 |
| **④ 배치 핸드오프** | 모아서 lock·깨우기 1회 |
| **⑤ K워커 + accountId%K** | 같은 유저=같은 워커(순서 역전 방지). **현재 K=1** — 분배식은 K 확장 대비로 구현해 뒀고, K 스윕은 미실시 |
| **⑥ 백프레셔(큐 상한)** | 큐 폭증 시 초과분 드롭 — 위치라 허용(다음 주기·종료가 커버) |
| **⑦ 종료 전원 저장** | 유실 방지 우선 → dirty 무관 전원 저장 |
| **⑧ 재연결 + 소켓 타임아웃** | DB 죽어도 서버 유지 — 주기마다 재연결(타임아웃으로 무한대기 방지) |
| **⑨ prepared statement** | SQL 틀을 미리 파싱해두고 값만 바꿔 실행 — 파싱 절감 · 값·문법 분리로 인젝션 차단. 단 위치 저장은 fsync가 진짜 병목이라 성능 이득은 작고, 오히려 **커넥션에 종속된 stmt의 생명주기 관리**가 핵심 (아래에서 자세히) |
| **⑩ 부팅 fail-fast** | 시작 때 K 커넥션 중 하나라도 실패하면 서버 미기동(설정·DB 오류 조기 발견). ⑧과 반대 방향 — **부팅은 엄격, 운영 중은 관대** |

## ⑨ prepared statement

> [그림: 04_prepared_stmt]

prepared statement는 **SQL 틀을 미리 파싱**해두고, 실행할 때 값만 갈아끼우는 방식이다. 얻는 건 두 가지 — 매번 문법을 다시 분석하지 않고(파싱 절감), 값과 문법이 분리돼 SQL 인젝션이 원천 차단된다.

### 위치(변경데이터) 저장에선 성능 이득 작음

prepared statement가 아끼는 건 *파싱 시간*(수 µs 수준)이다. 하지만 위치 저장은 실행할 때마다 MySQL이 커밋하며 로그를 디스크에 **강제로 밀어 쓴다(fsync)** — 이게 수백 µs~ms로 압도적으로 크다. 전체 시간의 대부분이 이 디스크 대기라, 파싱을 아껴도 티가 안 난다.

→ 진짜로 줄이려면 여러 저장을 **모아서 한 번에 커밋**해 fsync 횟수를 낮춰야 한다 (아래 *다음 단계*의 배치 커밋).

### 진짜 이유는 성능이 아니라 "생명주기 관리"

stmt 핸들은 **특정 커넥션 위에서** 만들어진다. 그래서 그 커넥션이 죽으면 stmt도 같이 무효가 된다. 이 종속 관계 탓에 커넥션의 모든 국면마다 stmt를 짝맞춰 관리해야 한다.

| 국면 | stmt 처리 |
| --- | --- |
| **재연결마다** | 새 커넥션 위에 stmt를 다시 준비 (옛 stmt는 이미 무효) |
| **준비 실패 시** | 방금 연 커넥션을 도로 닫음 — stmt 없는 반쪽 커넥션을 안 남긴다 |
| **정상 종료 시** | stmt 먼저 닫고 → 커넥션 닫음 |
| **커넥션 유실 감지 시** | stmt·커넥션 둘 다 닫고, 다음 주기에 재연결 |

핵심 규칙 — **stmt는 항상 커넥션보다 먼저 닫는다** (종속 관계라 순서를 지킨다).

### 실행 경로 — 워커 전용 버퍼에 값만 갈아끼운다

stmt와 커넥션은 스레드 안전하지 않으므로 **워커마다 전용으로** 하나씩 가진다 (accountId%K로 같은 유저는 늘 같은 워커 → 공유 없음).

- **준비 단계**: 바인딩 버퍼가 워커 슬롯의 값 주소를 가리키도록 딱 한 번 연결
- **실행 단계**: 그 버퍼에 이번 값만 복사 → execute만 호출 (재파싱·재바인딩 없음)

## 큐마다 실패 정책이 다르다

> [그림: 05_resilience]

"무엇이 진실이냐"에 따라, 큐가 가득 찼을 때 대응이 갈린다.

| 큐 | 실패 시 | 이유 |
| --- | --- | --- |
| 수신·송신 (네트워크) | **세션 종료** | 유실·순서 꼬임 = 상태 불일치, 되돌릴 수 없음 |
| DB 저장 | **잡만 드롭** (세션 유지) | 최신화가 늦어질 뿐, 게임은 메모리로 정상 |

> "드롭"의 대상이 다르다 — 전달 큐는 **세션을 끊고**, DB 큐는 **잡만 버린다**. "메모리가 진실"이라는 원칙에서 나온 차이다.

이 원칙이 서버 전체 8개 지점에서 어떻게 갈리는지는 9장 「과부하 정책」 참조 (수신·송신 링버퍼·패킷 검증·세션 풀·로그 큐까지).

## 관측 지표 (Prometheus → Grafana)

- **saved / failed** — 처리량 / DB 오류·커넥션 끊김
- **dropped** — 과부하로 버린 저장 잡 (= 워커 증설 신호)
- **queue_depth (워커별)** — 어느 워커가 병목인지, 분배가 고른지

## 요약

> 게임 루프를 **막지 않는** 비동기 저장 — 선별 저장 · 순서 보장(accountId%K) · 과부하 제어 · 장애 자동 복구. 실패 정책은 큐 성격에 맞췄다(전달 큐=세션 종료, DB=잡 드롭). 모두 **"메모리가 진실"** 한 원칙에서 나온다.
