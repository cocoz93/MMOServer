# 리눅스 포팅 문서화 계획

포팅 작업을 노션에 남기는 순서. **코드 작업이 아니라 글 작업**이라 판정 기준이 다르다 —
빌드가 통과하는지가 아니라, **쓴 문장이 코드와 맞는지 · 나중에 읽고 설명할 수 있는지**를 본다.

## 이 문서를 쓰는 법 (루프 작업 규칙)

**이 문서가 진행 상태의 정본이다.** 시작할 때 여기부터 읽고, 체크가 안 된 첫 페이즈 **하나만** 한다.

### 페이즈 하나를 끝내는 절차

1. **작업** — 페이즈 본문에 적힌 것을 한다
2. **판정** — 페이즈에 붙은 판정 기준을 실제로 확인한다. 눈으로 훑고 넘어가지 않는다
3. **자가검증** — 이번 페이즈에 **새로 쓴 주장**을 코드·실측과 다시 대조한다.
   틀린 게 나오면 노션을 고치고, 그게 페이지의 결론을 뒤집으면 페이즈를 다시 연다.
   *범위는 이번에 새로 쓴 것까지다 — 앞 페이지를 매번 재감사하지 않는다*
4. **기록** — `- [ ]` → `- [x]`, 판정 결과를 한 줄로. 노션 URL을 같이 적는다
5. **취합** — 상위 페이지에 링크가 제자리에 붙었는지 확인하고, 이 문서에 반영한다
6. **커밋** — 메시지는 **개조식**(명사형 종결), 트레일러 없음. **push는 하지 않는다**

### 글 작업이라서 더 지키는 것

- **주장에는 근거를 단다** — 파일:줄, 명령, 수치. "빠르다 · 깔끔하다" 같은 형용사만 남기지 않는다
- **모르는 채로 그럴듯하게 쓰지 않는다.** 이게 이번 문서화의 제1 규칙이다.
  epoll·리눅스는 아직 손에 익지 않았다. 확인 없이 매끄럽게 써두면 **면접에서 그 문장을 설명하지 못한다.**
  확인 못 한 것은 지우거나 **「확인 대기」** 로 남긴다 — 남겨두는 편이 낫다
- **페이지마다 「직접 확인해 보기」를 단다** — 그 주장을 본인이 되짚을 수 있는 명령이나 코드 위치.
  읽는 사람이 내 말을 믿고 넘어가는 자리를 만들지 않는다
- **덜어내는 쪽이 기본** — 기록용 5장은 압축한다. 깊이는 개념 페이지에서만 준다
- 노션 편집 함정: 큰 `old_str`은 타임아웃 → 청크로 쪼갠다. 한글은 이스케이프하지 말고 그대로 넣는다.
  표는 colgroup 정규화 때문에 매칭이 어긋날 수 있다

### 루프를 멈추는 때

- **`D7`까지 끝나면 정지한다.** 6번(성능 비교)은 측정이 전제라 이 루프에 없다 —
  PC 노이즈 때문에 측정을 미뤄둔 상태이고, 그건 `LINUX_PORT_PLAN.md`의 5·6단계 소관이다
- 정지할 때 **「확인 대기」에 모인 것을 함께 보고한다.** 그게 다음 작업 거리다

### 막혔을 때

- 판정을 못 넘겼으면 `- [!]`로 두고 막힌 지점을 적은 뒤 **다음 페이즈로 간다**
- **개념이 안 잡혀서 막히는 것**은 정상이다. 얼버무리지 말고 `D1`(epoll 개념)로 돌아가 그 대목을 보강한다
- 사람이 판단해야 하는 것(글의 방향·수위)은 혼자 정하지 말고 선택지를 남긴다

## 확정 골격

**두 갈래로 나눈다.** 노션에 이미 있는 방식 그대로다 — 개념은 「서버 아키텍처」에(`io_uring`·`RIO` 옆),
구현 기록은 별도 페이지에(`RIO 서버 구현`처럼).

### 갈래 ① 개념 — 공부용

| 페이지 | 위치 | 담는 것 |
|---|---|---|
| **epoll** | 「서버 아키텍처」 콜아웃 | 준비 통지란 무엇인가 · IOCP의 완료 통지와 무엇이 다른가 · ET/LT · `EPOLLOUT` · **왜 스레드 모델이 따라 바뀌는가** |

### 갈래 ② 기록 — 포폴용 (「리눅스 포팅」 하위 5장)

| | 페이지 | 담는 것 |
|---|---|---|
| 1 | **왜 옮겼나 · 결과** | 동기 · CMake로 한 소스 두 OS · 에코 PoC로 길 내기 · 결과 화면 |
| 2 | **락프리를 리눅스로** | 자료구조 코드 **무변경** · 16바이트 CAS `__sync` 실측 · 힙/TLS는 표 한 줄 |
| 3 | **두 모델 차이가 터진 곳** | `NetIoModel` 헛다리 → **참조를 누가 놓는가** · **제출과 완료가 붙어버린다** |
| 4 | **네트워크 밖의 Windows 의존** | Platform 격리 · 전송 경계 15개 · **크래시 덤프** · 기존 Windows 팔도 고쳤다 · 잔가지 표 |
| 5 | **검증** | 테스트 6종 양 OS 일치 · 크로스 OS 통신 · Windows 양팔 회귀빌드 · 재검증 3건 |

측정이 끝나면 **6. 성능 비교**를 붙인다 (지금은 PC 노이즈 때문에 보류).

### 작성 순서

**개념 → 2 → 3 → 4 → 5 → 1.**
1번(왜/결과)은 아래가 다 나온 뒤에 써야 요약이 정확하다.
개념을 맨 앞에 두는 이유는, 그게 서야 3번의 "왜 이게 문제였나"가 **본인 말로** 나오기 때문이다.

  `EpollWorkerThread`가 `EPOLLHUP|EPOLLERR|EPOLLRDHUP`를 **`EPOLLIN`보다 먼저** 검사해
  바로 `RequestDisconnectSession`으로 간다(`Transport_Epoll.cpp:367-371`).
  상대가 FIN을 보냈어도 수신 버퍼에 아직 안 읽은 데이터가 남아 있을 수 있는데, 그 경우 그대로 버려진다.
  같은 통지에 `EPOLLIN`이 함께 서 있으면 먼저 읽고 나서 끊는 것이 안전하다.
  **다만 재현 하네스도 실측도 없다** — 결함으로 단정하지 않고 관측 대기로 둔다.
  (게임 프로토콜상 종료 직전 패킷이 유실돼도 문제가 없을 수 있다. 판단하려면 시나리오가 필요하다)
