# 3. 16바이트 CAS — `__atomic`은 함수 호출을 낸다 ★
이 문서에서 유일하게 길게 쓸 대목이다.
## 왜 16바이트인가
이 자료구조는 ABA 문제를 **포인터와 카운터를 붙여 한 번에 교환하는** 방식으로 푼다. 포인터 8바이트 + 카운터 8바이트 = **16바이트를 원자적으로 바꿔야** 하고, x86-64에서 그 명령이 `cmpxchg16b`다. Windows에서는 `InterlockedCompareExchange128`이 그 명령으로 내려갔다.
GCC에는 이걸 쓰는 방법이 둘이다.
- `__atomic_compare_exchange_n` — **요즘 방식**. C++11 메모리 모델을 그대로 반영한다
- `__sync_val_compare_and_swap` — **옛 방식**(legacy). GCC 4 시절 것이고, 항상 full barrier다
당연히 앞의 것을 골랐다. 그리고 그게 틀렸다.
## 실측 — 같은 플래그로 컴파일한 두 함수
```c++
typedef __int128 i128;
bool sync_cas(i128* p, i128 cmp, i128 val) {
    return __sync_val_compare_and_swap(p, cmp, val) == cmp;
}
bool atomic_cas(i128* p, i128* cmp, i128 val) {
    return __atomic_compare_exchange_n(p, cmp, val, false, __ATOMIC_SEQ_CST, __ATOMIC_SEQ_CST);
}
```
```bash
g++-13 -O2 -mcx16 -c cas16.cpp && objdump -d cas16.o
```

<callout icon="🚫" color="red_bg">
	**`-mcx16`****을 줬는데도 그렇다.** 그 플래그는 "이 CPU에 `cmpxchg16b`가 있다"고 알려주는 것이고, GCC는 16바이트 `__atomic`에 대해서는 그걸 알고도 인라인하지 않는다.
	핫패스에서 CAS 한 번이 **명령 하나에서 함수 호출로** 바뀐다. 락프리 자료구조에서 이건 그냥 넘길 차이가 아니다.
</callout>
그래서 **16바이트 CAS 어댑터만 옛 ****`__sync`**** 계열을 쓴다.** 나머지(8바이트 증감, 16비트 증감, 포인터 CAS)는 `-mcx16` 없이도 `__atomic`이 인라인(`lock xaddq`·`lock xaddw`·`lock cmpxchgq`)이라 그대로 뒀다.
<callout icon="💡" color="gray_bg">
	`__sync_val_compare_and_swap`은 **"연산 전 값"**을 돌려준다. 성공했다면 정의상 그 값이 기대값과 같으므로, **비교 자체가 성공 판정**이 된다. 실패면 관측값을 `comparandResult`에 써서 돌려주는데, 이게 MSVC `InterlockedCompareExchange128`의 in/out 규약과 정확히 같아서 호출부를 안 고쳐도 됐다.
</callout>
# 4. 방어막을 어디에 세우나
문제는 **이게 조용하다는 것**이다. `-mcx16`을 빠뜨려도 컴파일은 되고, 실행도 된다. 다만 락프리인 줄 알았던 자리가 libatomic의 뮤텍스 폴백으로 내려갈 수 있다. **락프리를 쓰려고 만든 자료구조가 락을 쓰게 된다.**
컴파일 단계에서 막아야 하는데, 자연스러운 후보가 안 통한다.

```c++

    #error "16-byte CAS cannot be inlined here: add -mcx16. Without it the 128-bit CAS degrades to a libatomic call."
#endif
```
<callout icon="✅" color="green_bg">
	`-mcx16`은 CMake의 UNIX 분기에 **전역**으로 걸었다(`add_compile_options(-mcx16)`). 타겟마다 거는 대신 전역으로 둔 이유는, 앞으로 추가될 타겟이 이걸 빠뜨릴 일이 없게 하기 위해서다.
	libatomic 링크는 필요 없다 — `__sync` 경로가 인라인이라 외부 호출이 남지 않는다.
</callout>
# 5. 나머지 함정 둘
<callout icon="🕳️" color="gray_bg">
	**① ****`_aligned_malloc`****은 인자 순서가 반대다.**
	MSVC는 `_aligned_malloc(size, alignment)`인데 POSIX는 `posix_memalign(ptr, alignment, size)`다. 그대로 바꿔 끼우면 **크기와 정렬이 뒤바뀐 채 컴파일도 실행도 된다.** 어댑터가 순서를 맞춰 넘긴다.
</callout>
<callout icon="🕳️" color="red_bg">
	**② ****`ULONG`****·****`DWORD`****를 ****`unsigned long`****으로 두면 폭이 어긋난다.**
	Windows에서 이 둘은 **32비트**다. 그런데 리눅스 LP64에서 `unsigned long`은 **64비트**다. 처음에 `unsigned long`으로 별칭을 걸었다가, 나중에 다른 헤더가 같은 이름을 `uint32_t`로 정의하면서 `conflicting declaration`으로 터졌다.
	지금은 `std::uint32_t`로 고정해 뒀다. **컴파일 에러로 드러나서 다행이었던 종류의 실수**다 — 조용히 넘어갔다면 구조체 크기가 달라지는 문제로 이어졌을 수 있다.
</callout>
## 힙 API를 표준 할당자로 바꾼 판단
원본은 `HeapCreate`로 **전용 힙**을 만들고 `HeapSetInformation`으로 저단편화 힙(LFH)을 켠다. 리눅스에는 대응물이 없어 설계 판단이 필요했다.
조사해 보니 **힙 API가 전부 콜드 패스**였다.
- `HeapAlloc` — `AllocNewNode()` 안에서만. 이 함수는 `__declspec(noinline)`이 붙은 **"프리리스트가 비었을 때만 도는"** 경로다. 정상 운영에서는 사전 적재로 채워두므로 거의 안 불린다
- `HeapFree` — 소멸자의 정리 루프에서만. `Free()`는 노드를 프리리스트로 되돌릴 뿐 해제하지 않는다
- `HeapDestroy` — 소멸자 끝에 1회
그래서 `malloc`으로 옮겨도 핫패스에 닿지 않는다. **전용 힙을 ****`mmap`**** 아레나로 재현하는 것은 이 용도에 과잉**이라 하지 않았다.
<callout icon="⚠️" color="orange_bg">
	**한 가지 달라지는 점을 기억해 둘 것** — `HeapDestroy`는 힙을 통째로 반환하므로 아직 반납되지 않은(사용 중) 노드의 메모리까지 회수된다. `malloc` 경로에는 그런 일괄 회수가 없어, 소멸 시점에 사용 중이던 노드는 `free`되지 않는다.
	소멸자는 프로세스 생애 1회라 실질 영향은 없지만(OS가 회수한다), **ASan이나 valgrind에는 누수로 잡힌다.** 그렇게 보이면 이 대목이 판단 근거다.
</callout>
