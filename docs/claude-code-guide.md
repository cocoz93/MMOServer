# 클로드 코드 운영 가이드

> 숙련 서버/백엔드 개발자 대상. 목적은 **클로드 코드 자체를 이해하고 숙달**하는 것.
> 예시는 게임서버 맥락으로 들되, 특정 저장소에 매이지 않는 **일반 가이드**다.
> 성격: 설명서 복제본이 아니라 **지도 + 실전 예제 + 공식 문서 링크**. 잘 변하는 디테일(명령·플래그)은 공식 문서에 위임하고, 안 변하는 것(개념·언제 쓰나·어떻게 조합하나)에 무게를 둔다.
> 정본은 이 md(git 추적), 발행은 안정된 파트만.

---

## 이 문서 쓰는 법

- **대상**: 설치·터미널·기초 실습은 아는 개발자. 그 부분은 생략한다.
- **순서 자유**: 위→아래로 안 읽어도 됨. 관심(하네스·루프)부터 골라도 됨. 익히면 체크박스 `[x]`.
- **표기 규칙**
  - `〔건너뛰기〕` — 숙련 개발자에겐 불필요한 입문 파트. 이유 병기.
  - `〔문서: X〕` — 공식 문서의 해당 페이지에 위임(잘 변하는 것). URL은 확인된 것만.
  - `↔ 책1/책2` — 참고한 두 책의 해당 장. **누락 점검용**(구조로 쓰는 게 아님).
  - `〔해보기〕` — 지금 바로 해볼 실습.
- **최신성 규칙**: 명령/플래그가 공식 문서와 다르면 **공식 문서가 정본**. 현재 쓸 수 있는 명령·스킬은 `/help`로 확인(환경·버전 따라 다름).
- **공식 문서 허브**: `https://code.claude.com/docs/`

## Part 1. 놓쳤을 기본기  ↔ 책1 2.9·3.6·4.1

매일 쓰면서 놓치기 쉬운 흐름, 모드 전환, 되돌리기, 컨텍스트 관리.

- [ ] **실행 모드 & Shift+Tab 전환** — 권한 요구 정책을 세션에서 즉시 전환.
  - **왜 중요**: 작업 성격에 따라 정책이 달라야 효율적. 반복 편집 땐 자동수락, 위험한 변경(스키마·배포) 땐 수동, 코드 흐름 파악 땐 읽기만.
  - **해보기**: `Shift+Tab`을 누르면 상태바가 바뀐다. 기본 cycle은 `default`→`acceptEdits`→`plan`. 한 바퀴 돌려보고 다시 `default`로 복귀.
  - **주의/핵심**:
    - `default`(수동): 매 명령마다 승인. 민감 작업에 맞음.
    - `acceptEdits`: 파일 편집·일반 파일 명령 자동 수용, 나머지 Bash는 여전히 물음. 워킹 디렉토리 안에서만.
    - `plan`: 읽기만. 쓰기 전혀 안 됨. 탐색→계획→(승인)→구현.
    - `bypassPermissions`: 권한 검증 없음. **컨테이너/VM 전용**.
    - `auto`(있으면): 분류기가 배경에서 위험도 검증. 활성 조건은 공식 문서로 확인.
  - 〔문서: Permission modes〕 · `https://code.claude.com/docs/en/permission-modes.md`

- [ ] **Plan 모드 → 승인 흐름** — 복잡한 수정은 계획 먼저, 검토 후 구현.
  - **왜 중요**: 여러 파일이 얽힌 변경(예: 스레드 풀 구조 교체, 브로드캐스트 경로 리팩터)은 바로 손대면 실패율·컨텍스트 낭비가 커진다. 계획 읽고 OK 하는 몇 초가 전체 그림을 맞춘다.
  - **해보기**: `plan` 진입 → "이 기능을 넣을 때 수정할 파일과 순서를 계획해줘" → 읽기만으로 계획 제시 → 승인/추가계획/편집 선택 → 승인 후 구현 모드로.
  - 〔문서: Permission modes — plan mode〕

- [ ] **Esc / `/rewind` 되돌리기** — 잘못된 편집·탐색 중단, 코드와 대화를 이전으로 복구.
  - **왜 중요**: 실험하다 "이 방향 접자" 할 때 코드까지 한 번에 되돌린다.
  - **해보기**: 편집 중 `Esc`로 즉시 중단(대화·코드 보존). `Esc` 두 번 또는 `/rewind` → 메뉴: 대화만 / 코드만 / 둘 다 복구.
  - **주의/핵심**: `/rewind`는 **Claude가 만든 변경만** 추적. 셸 명령(`rm`, `sed` 등)으로 바꾼 건 git으로 복구. 복구 후 `git status` 확인.
  - 〔문서: Commands — Utilities〕

- [ ] **`/model` & `/fast`** — 세션 중간에 모델 전환, 확장 사고 조절.
  - **왜 중요**: 상위 모델 구독이라도 가벼운 질문·간단 리뷰엔 더 빠른 모델/빠른 출력이 효율적.
  - **해보기**: `/model` → 선택기(또는 `/model sonnet` 직접). `/fast`로 빠른 출력 토글. 정확한 인자 문법은 `/help`로 확인.
  - 〔문서: Commands — Model & Performance〕

- [ ] **컨텍스트 관리: `/clear` & `/compact`** — 긴 세션에서 관계없는 내용 버리기.
  - **왜 중요**: 한 작업(예: 송신 경로 실험)을 끝내고 다른 작업으로 넘어갈 때, 앞 작업의 코드·열어본 파일이 컨텍스트에 쌓여 있으면 무관한 토큰만 소비. `/clear` 해도 CLAUDE.md·메모리는 자동 재로드.
  - **해보기**: 작업 끝나면 `/clear`. 긴 세션 중간엔 `/compact "직전 변경만 보존"`. `/context`로 현재 사용량·최적화 제안 확인.
  - 〔문서: Context window〕

- [ ] **첨부·참조: `@파일` & 이미지 붙여넣기** — 프롬프트에서 파일·스크린샷 직접 인용.
  - **왜 중요**: 프로파일러 그래프·크래시 로그·헤더를 말로 설명하는 대신 붙이면 컨텍스트 절약·정확.
  - **해보기**: 이미지 = 클립보드 Ctrl+V 또는 드래그. 파일 = `@경로/헤더.h`. 디렉토리 참조 시 트리 표시.
  - 〔문서: Best practices — rich content〕

- [ ] **프롬프트 작성 3요소** — 범위·컨텍스트·검증 방법 명시.
  - **왜 중요**: "코드 리뷰해줘"는 뭉뚱그려짐. "이 함수는 락프리·특정 CAS 제약. @큐.cpp에서 해당 호출 찾아 검증하고, 틀리면 수정 후 테스트"처럼 구체화하면 정확한 결과가 빨리 나온다.
  - **해보기**: 매 프롬프트에 ① 범위("이 파일만"/"공개 API는 건드리지 말고") ② 컨텍스트("Release 빌드 기준"/"@CLAUDE.md 참고") ③ 검증("빌드 후 테스트"/"before/after 비교").
  - 〔문서: Best practices — specific context〕 · ↔ 책1 3.6

**치트시트**
- `Shift+Tab`: 모드 cycle · `Esc`: 즉시 중단 · `Esc`×2 또는 `/rewind`: checkpoint 메뉴
- `/model [모델]`·`/fast`: 모델/속도 · `/clear`: 컨텍스트 리셋(메모리 유지) · `/compact [지시]`: 요약
- `/context`: 컨텍스트 상태 · `@경로`: 파일/디렉토리 참조 · 이미지: Ctrl+V/드래그

## Part 2. 코드 품질 게이트 (매일 쓸 것)  ↔ 책1 6장

매일 커밋 전에 돌릴 점검들. 각 도구는 한 가지에 집중하므로 순서대로 거쳐야 진짜 문제가 보인다.

- [ ] **`/code-review`** — 현재 브랜치 diff를 자동 점검하고 버그·설계·중복 지적.
  - **왜 중요**: 버퍼 경계(off-by-one), 동시성 로직 오류, 최적화 코드의 미묘한 버그를 커밋 전에 잡는다. 시스템 코드일수록 값어치.
  - **해보기**: 커밋 직전 `/code-review high`. 필요하면 `--fix`로 지적을 워킹트리에 적용, `--comment`로 PR 인라인 코멘트.
  - **주의/핵심**: 효과 레벨 `low`·`medium`은 높은 확신만(오탐 적음), `high`~`max`는 폭넓게. 시스템·동시성 코드는 `high` 이상 권장. 대규모 변경은 `ultra`(클라우드 다중 에이전트 심층)도 있으나 사용자가 직접 트리거. `--fix` 후 로컬 빌드로 검증.
  - 〔문서: Code Review〕 · ↔ 책1 6.8

- [ ] **`/security-review`** — 대기 중 변경을 보안 관점으로 스캔.
  - **왜 중요**: 네트워크 패킷처럼 **신뢰 못 할 입력**을 다루는 경로의 버퍼 오버런·정수 오버플로·검증 누락을 커밋 전에 거른다.
  - **해보기**: 입력 파싱·인증·직렬화 경로 수정 커밋 직전 실행. "새로 추가된 위반"에 집중(기존 문제와 구분).
  - **주의/핵심**: 리포트를 근거(파일·라인)로 확인하고 수동 처리. 자동 수정 과신 금물. 매 틱 실행되는 핫패스와 외부 입력 경로에 특히 유의.
  - 〔문서: Security Review〕 · ↔ 책1 6.4

- [ ] **디버깅·원인추적** — "로컬은 되는데 릴리즈/부하에서만" 문제.
  - **왜 중요**: 특정 부하에서만 나는 세션 누수, 특정 설정 조합에서만 나는 성능 급락처럼 "문제는 분명한데 원인이 뭔가"인 현상.
  - **해보기**: 전용 명령을 찾기보다 **증상 + 재현 절차**를 정리해 맡기는 게 핵심. 예: 증상("동접 일정 수 이상이면 지연 급증") + 재현("특정 스레드/워커 조합, 부하 N") → 로그 집중도 올려 재현 → "언제·어디서 터졌나" 타임스탬프 대조.
  - **주의/핵심**: "로컬만 OK"는 보통 타이밍 경쟁(메모리 순서)이나 플랫폼 차이(캐시 라인·코어 수). **Release로 재현**(Debug는 최적화가 달라 아예 다름). flaky면 최소 3회 반복 — "1회 pass, 2회 fail"은 경쟁 신호.
  - **심화(네이티브)**: 크래시/코어 덤프의 콜스택을 붙여 원인 지목 요청, 로그는 `@참조`로. 최소 재현 코드를 같이 만들면 반복 검증이 쉬움. 동시성 의심이면 새니타이저(TSan/ASan) 출력을 붙여 해석 요청(MSVC는 대안 필요). 프로파일러 스냅샷·플레임그래프는 이미지로 붙여 핫스팟 해석.
  - 〔문서: common-workflows — Fix bugs〕 · ↔ 책1 6.2, 책2 Ch14

- [ ] **테스트 자동 생성·유지** — 회귀 방지.
  - **왜 중요**: 락프리 자료구조·동시성 코드를 리팩터한 뒤 corner case 누락은 메트릭으로만 잡으면 놓치기 쉽다. 단위테스트 + 부하/스모크 격자가 배포 전 신뢰도를 준다.
  - **해보기**: 새 로직·토글을 추가할 때 그 로직만 겨냥한 단위테스트 작성 + 스모크 범위 확대(파라미터 격자).
  - **주의/핵심**: 단위테스트는 개별 컴포넌트, 스모크는 왕복 흐름(client↔server). Release에서 테스트. flaky면 반복 실행으로 경쟁 여부 판별.
  - 〔문서: common-workflows — Work with tests〕 · ↔ 책1 6.5

- [ ] **문서화** — CLAUDE.md·`.claude/rules/`·팀 규칙.
  - **왜 중요**: 인코딩 규칙·빌드 순서·주의사항처럼 반복 설명거리를 파일로 고정하면 매번 재설명이 사라진다. "이거 왜 이렇게 했지?"를 반복하면 문서화 신호.
  - **해보기**: 새 규칙·결함 패턴을 CLAUDE.md에 한 줄로. 폴더별 특수 규칙은 `.claude/rules/`.
  - **주의/핵심**: CLAUDE.md = 항상 지킬 것, `.claude/rules/` = 폴더별 규칙. 커밋 메시지에 관련 규칙 근거를 인용하면 재현·리뷰가 쉬워짐.
  - 〔문서: Memory / CLAUDE.md〕 · ↔ 책1 6.6

- [ ] **레거시 분석·모듈 리팩터** — 오래된 코드 중복 제거·전략패턴.
  - **왜 중요**: 여러 파일이 같은 패턴을 복붙하거나 캐스팅을 반복하면 유지보수 비용이 커진다. 공통화로 줄인다.
  - **해보기**: 복잡도 높은 함수부터 → 호출처 개수를 세어 리팩터 가치 판단 → "이 함수들 공통 로직을 전략패턴으로 뺄 수 있을까" 질의. "함수 추출→모듈화→테스트 추가→스모크"로 작게 쪼갬.
  - **주의/핵심**: 중복 제거 후 성능 역행 주의(가상 호출 오버헤드 등). Release 마이크로벤치 확인. 한 커밋에 여러 파일 동시 수정 금지.
  - 〔문서: common-workflows — Refactor〕 · ↔ 책1 6.1·6.3

**하루 루틴**
1. 코드 변경 후 `/code-review high` → 버그·설계 점검(필요 시 `--fix`)
2. 보안 민감부 수정 시 `/security-review` → 입력 검증·경계 확인
3. 재현 안 되면 증상+재현법 정리해 로그 분석 의뢰
4. 새 기능·리팩터 후 단위테스트 추가 + 스모크 격자 확장
5. 발견한 규칙·결함 패턴은 즉시 CLAUDE.md 한 줄 추가
6. 주기적으로 레거시 모듈 1개 리팩터

## Part 3. 확장 프리미티브  ↔ 책1 4장

기본 도구보다 깊은 작업을 위한 6개 확장층: **커스텀 명령·스킬·서브에이전트·훅·MCP·플러그인**. 각각 다른 문제를 푼다.

### 커스텀 슬래시 명령
- [ ] **커스텀 슬래시 명령** — 자주 쓰는 프롬프트를 `/내명령`으로 부르는 파일(`.claude/commands/`).
  - **왜 중요**: 반복 지시(코드 감사 절차, 부하 실험 세팅)를 "매번 타이핑"에서 "파일 → `/명령`"으로. 인자($1 등)로 변형도 한 파일로.
  - **해보기**: 자주 쓰는 절차 하나를 `.claude/commands/`에 만들어 `/이름`으로 항상 같은 흐름 시작.
  - **주의/핵심**: 고정 프롬프트엔 커스텀 명령, 상황 판단 자동 실행엔 스킬(아래). 스킬은 자동 매칭 + 명시 호출 둘 다.
  - 〔문서: Custom slash commands〕 · ↔ 책1 4.2.1

### 스킬(Skill)
- [ ] **스킬** — 특정 작업용 지침 묶음(`.claude/skills/이름/SKILL.md`). frontmatter(description 등) + 본문. **Description이 호출을 결정**(자동 매칭), Progressive Disclosure(설명만 먼저 로드→필요 시 본문).
  - **왜 중요**: 자동 호출(요청이 description과 맞으면 알아서 실행)과 명시 호출(`/이름`) 둘 다 됨. 반복 작업의 절차를 캡슐화.
  - **해보기**: 새 스킬을 만들 때 description을 "도메인 용어 + 액션"으로 구체화("부하 실험 결과를 파싱해 A/B 비교")해야 자동 매칭이 정확.
  - **주의/핵심**: description이 짧고 구체적일수록 매칭이 정확. 도구 제한(allowed-tools)은 SKILL.md에 명시.
  - 〔문서: Skills〕 · ↔ 책1 4.2, 책2 Ch5

### 서브에이전트
- [ ] **서브에이전트** — 별도 컨텍스트로 병렬 탐색·전문 작업을 맡기는 하위 에이전트(`.claude/agents/` md).
  - **왜 중요**: 넓은 코드베이스를 영역별로 나눠(예: 네트워크 계층 / 세션 관리 / 로깅) 각기 다른 에이전트에 맡기면 **동시 병렬 + 결과는 텍스트만 + 컨텍스트 격리**. 큰 감사가 크게 단축.
  - **해보기**: 큰 검토를 두세 영역으로 나눠 각 서브에이전트에 위임(각각 Read/Grep/Glob만) → 결론만 취합. (이 문서도 Part 1·2·3을 서브에이전트 3개로 동시에 뽑았다.)
  - **주의/핵심**: 서브에이전트는 독립 컨텍스트라 필요한 맥락을 호출 프롬프트에 직접 넣어야 함. 새 에이전트 파일은 세션 재시작이 필요할 수 있음. 넓은 탐색엔 좋지만 세밀한 리뷰는 지침을 촘촘히.
  - 〔문서: Subagents〕 · ↔ 책1 4.3

### 훅(개요)
- [ ] **훅(hooks)** — 특정 이벤트(도구 실행 전/후, 세션 시작/종료 등)에 개입해 입력 수정·결과 필터·승인/거부를 하는 콜백. settings.json에 정의.
  - **왜 중요**: "앞으로 매번 X 하면 자동 Y"는 지침·메모리로는 안 되고 **훅으로 걸어야** 강제된다.
  - **해보기**: 개념만 여기서. **상세(이벤트 종류·matcher·차단)는 Part 4**에서 실제 규칙으로.
  - 〔문서: Hooks〕 · ↔ 책1 4.4

### MCP 심화
- [ ] **외부 MCP 서버 추가** — DB·이슈트래커·저장소 같은 외부 도구를 설정 파일(`.mcp.json`)이나 SDK로 연결.
  - **왜 중요**: 한 줄 설정으로 도구 수십 개를 붙임. 특화 서버라 범용 도구보다 인코딩·권한 문제가 적음.
  - **해보기**: `.mcp.json`에 서버 추가 후 그 도구를 허용 목록에 명시. 도구 이름 패턴은 `mcp__<서버명>__<액션>`.
  - **주의/핵심**: MCP 도구는 보통 명시 허가 필요(자동 아님). 인증 토큰은 env/headers로 주입. 정확한 필드는 공식 문서로 확인.
  - 〔문서: MCP〕 · ↔ 책1 4.5

### 플러그인 · 마켓플레이스 · LSP
- [ ] **플러그인** — 스킬·에이전트·훅·MCP를 한 패키지로 묶어 배포·재사용(디렉토리 + manifest).
  - **왜 중요**: 팀 공용 도구 묶음을 한 번에 설치·공유. 마켓플레이스 배포도 가능.
  - **해보기**: 플러그인 디렉토리에 `skills/…`·manifest를 구성해 로컬 로드부터. 정식 도입은 스킬이 몇 개 안정된 뒤.
  - **주의/핵심**: 마켓플레이스·LSP 세부는 버전 따라 다르니 공식 문서로 확인. 지금은 스킬+MCP로 충분, 플러그인은 재배포 필요할 때.
  - 〔문서: Plugins / Marketplace / LSP〕 · ↔ 책1 4.6

### 항목 간 연결
| 용도 | 도구 | 특징 |
| --- | --- | --- |
| 고정 프롬프트 반복 | 커스텀 명령 (`.claude/commands/`) | 파일 → `/이름` 호출, 인자 가능 |
| 자동+명시 실행 | 스킬 (`.claude/skills/…/SKILL.md`) | description 자동 매칭, Progressive Disclosure |
| 병렬 독립 탐색 | 서브에이전트 (`.claude/agents/`) | 컨텍스트 격리, 도구 제한, 결과만 반환 |
| 이벤트 자동화 | 훅 (settings.json) | 도구·세션 이벤트 개입, 거부/수정 |
| 외부 도구 소스 | MCP (`.mcp.json`/SDK) | DB·API 등, 명시 허가 필요 |
| 패키지 재배포 | 플러그인 (+ manifest) | 스킬+에이전트+훅+MCP 한 번에 |

> 현재 쓸 수 있는 스킬·MCP 목록은 `/help`와 설정 파일로 확인(환경·버전 따라 다름).

## Part 4. 자동화 & 루프  〔관심〕

"매번 손으로 하던 것"을 자동으로. 훅은 규칙 강제, 루프·스케줄은 반복 작업, 백그라운드는 오래 걸리는 일 뒤로 돌리기.

- [ ] **훅(hooks)으로 규칙 강제** — 특정 이벤트(도구 실행 전/후, 응답 종료 등)에 셸 명령을 자동 실행.
  - **왜 중요**: CLAUDE.md에 적은 규칙(예: 커밋 전 Release 빌드, 특정 파일 편집 금지)은 "지침"이라 지켜질 수도 안 지켜질 수도 있음. 훅은 하네스가 직접 실행하므로 **강제**가 됨.
  - **해보기**: `update-config` 스킬로 "PostToolUse 훅: 소스 편집 후 빌드 실행" 하나만 걸어보기. 또는 특정 확장자 파일을 편집 도구로 건드리면 경고/차단.
  - **주의/핵심**: 훅은 내(Claude)가 아니라 **하네스가 실행**한다. "매번 X면 자동 Y"는 반드시 훅으로 걸어야 실현됨. 주요 이벤트: 도구 실행 전(PreToolUse, 차단 가능)·후(PostToolUse), 프롬프트 제출, 응답 종료(Stop) 등. 정확한 이벤트명·전달 방식(stdin JSON)은 공식 문서 대조.
  - 〔문서: Hooks〕 · ↔ 책1 4.4

- [ ] **`/loop`** — 프롬프트나 슬래시 명령을 주기적으로 반복. 간격을 주거나 생략하면 모델이 스스로 페이스를 정함.
  - **왜 중요**: 장시간 작업(부하 테스트·수집)을 "돌려놓고 주기적으로 상태 확인"하는 폴링 루프로.
  - **해보기**: 오래 걸리는 작업을 걸어둔 뒤 `/loop`로 "상태 확인 후 이상 있으면 알려줘"를 반복.
  - **주의/핵심**: 하네스가 추적하는 백그라운드 작업(서브에이전트·백그라운드 명령)은 끝나면 자동으로 깨우므로 폴링 불필요. 루프는 **하네스가 못 보는 외부 상태**(외부 CI·원격 큐)를 지켜볼 때 값어치가 큼.
  - 〔문서: /loop (환경의 스킬)〕

- [ ] **스케줄 / 루틴(routines)** — cron 일정으로 도는 클라우드 에이전트.
  - **왜 중요**: "매일 밤 회귀 테스트 돌리고 결과 요약" 같은 정기 작업을 자리에 없어도 실행.
  - **해보기**: `schedule` 스킬로 가벼운 것부터 등록.
  - **주의/핵심**: 클라우드에서 도는 형태라 **로컬 저장소·대화형 인증 MCP는 없을 수 있음**. 로컬 빌드 의존 작업엔 안 맞을 수 있으니 범위 확인.
  - 〔문서: 스케줄/루틴 (환경의 스킬)〕

- [ ] **백그라운드 작업** — 오래 걸리는 명령·서브에이전트를 뒤로 돌리고 완료 시 알림.
  - **왜 중요**: 긴 수집·큰 빌드를 앞단에서 붙잡을 필요 없음. 뒤로 돌리고 다른 작업 병행.
  - **해보기**: 다음 긴 명령을 백그라운드로 실행하고 그동안 다른 일을 병행.
  - **주의/핵심**: 완료 시 하네스가 다시 깨움 → `sleep`으로 기다리거나 짧은 루프로 폴링하지 말 것.
  - 〔문서: 백그라운드 실행〕

## Part 5. 하네스 엔지니어링  〔관심·핵심〕  ↔ 책2 전체

> **번역 주의**: 책2의 팀 프리미티브(`TeamCreate` 등)와 이 환경의 실제 도구가 1:1로 안 맞을 수 있다.
> 여기선 개념을 소개하되, **실제 되는 것**(Workflow 도구·서브에이전트·팀 도구)으로 번역한다.
> 이 환경에는 다단계 오케스트레이션용 **Workflow 도구**와 팀 도구(TaskCreate·SendMessage 등)가 있으나, **명시적으로 요청해야 켜진다** — 아무 작업에나 자동으로 대군을 안 띄운다.

- [ ] **하네스란 무엇인가** — 모델 자체가 아니라 모델을 **둘러싼 구조**("around the model"). 에이전트 배치·역할 분리·검증 루프가 결과를 좌우한다.
  - **왜 중요**: "AI 작업의 병목은 능력이 아니라 배치·구조". 혼자 도는 에이전트는 제 실수를 못 보므로, 만드는 쪽과 검사하는 쪽을 분리해야 품질이 오른다. 성능을 코드 구조로 푸는 감각과 같다.
  - **해보기**: 혼자 시켰다가 놓친 실수 하나를 떠올려, "생성 에이전트 + 검증 에이전트"로 나눴다면 걸렸을지 사고실험.
  - 〔문서: 서브에이전트·Workflow 개념〕 · ↔ 책2 Ch1

- [ ] **3기둥: 에이전트 · 스킬 · 오케스트레이터** — 누가(에이전트)·어떻게(스킬)·누가 지휘(오케스트레이터)를 파일로 분리. 한 곳에 다 넣으면 무너진다.
  - **왜 중요**: 이 3분할을 의식하면 재사용·디버깅이 쉬워진다.
  - **해보기**: 자주 하는 작업 하나를 "에이전트 정의(무엇을 보나)/스킬(어떤 절차로)/오케스트레이터(몇 명을 어떻게 묶나)"로 3분할.
  - 〔문서: Subagents · Skills〕 · ↔ 책2 Ch3~6

- [ ] **Workflow 도구 = 결정론적 오케스트레이터** — 스크립트(JS)로 여러 서브에이전트를 정해진 제어흐름(루프·조건·팬아웃)으로 돌리는 도구. `agent()`(에이전트 1명), `parallel()`(동시·배리어), `pipeline()`(단계별·배리어 없음).
  - **왜 중요**: "설정 N개 × 같은 절차"를 손으로 반복하던 걸 결정론적으로 팬아웃(구체 레시피는 Part 6).
  - **해보기**: `pipeline([설정들], 실험실행, 지표수집, 판정)` 골격을 스케치. 단계 사이에 모두를 기다릴 필요 없으면 `parallel`(배리어) 대신 `pipeline` 기본.
  - **주의/핵심**: 서브에이전트는 **최종 텍스트만** 돌려줌 → 구조가 필요하면 schema(구조화 출력) 옵션. 동시 실행 수는 자동 상한(코어 기반)이라 항목이 많아도 안전.
  - 〔문서: Workflow/오케스트레이션 (환경 도구)〕 · ↔ 책2 Ch6

- [ ] **6가지 아키텍처 패턴** — 팀에는 모양이 있다. 상황에 맞는 배치를 고른다.
  - **왜 중요**: 아래 대응만 알아도 대부분 커버.
    - 파이프라인(순서가 의미) → `pipeline()`. 예: 수집→정제→판정.
    - 팬아웃/팬인(같은 입력, 다른 관점) → `parallel()` 후 병합. 예: 한 결함을 여러 관점으로 검증.
    - 전문가 풀(라우터+전문가) → 분류 에이전트 후 전문 에이전트로 라우팅.
    - 생성-검증(만들고 검사하고 다시) → 생성 + 검증 에이전트 루프.
    - 감독자(런타임 동적 분배) → 결과 보고 다음 작업을 즉석 결정.
    - 계층적 위임(총괄→팀장→실무자) → 큰 작업을 단계로 쪼갬.
  - **해보기**: 큰 감사에 "팬아웃(영역별 탐색)→팬인(중복 제거)→생성-검증(각 지적 반대심문)"을 얹어보기.
  - 〔문서: 오케스트레이션 패턴〕 · ↔ 책2 Ch8

- [ ] **팀 프리미티브 (TaskCreate · SendMessage)** — 공유 작업 큐(depends_on 의존)와 에이전트 간 직접(피어) 메시지 채널.
  - **왜 중요**: Workflow가 "정해진 대본"이라면, 팀 프리미티브는 "에이전트들이 서로 메시지 주고받으며 협업"하는 더 동적인 형태.
  - **해보기**: 지금은 개념만. 대부분은 Workflow(결정론적)로 충분함을 인지. 피어 협업이 꼭 필요할 때만 도입.
  - **주의/핵심**: 책2가 강조하는 "폭주·정리 누락"이 실제 위험. 팀은 반드시 종료(정리)까지.
  - 〔문서: 팀/Task 도구 (환경 도구, 지원 범위 확인)〕 · ↔ 책2 Ch6

- [ ] **실행 모드 선택: 팀 vs 서브에이전트 vs 하이브리드** — 언제 정식 팀을 짜고, 언제 각자 시킬지.
  - **왜 중요**: 대부분의 작업(감사·스윕)은 **결정론적 팬아웃(Workflow/서브에이전트)** 이면 충분. 서로 실시간 협의가 필요한 경우만 팀.
  - **해보기**: 다중작업 시작 전 "대본대로면 되나(→Workflow), 서로 대화가 필요한가(→팀)?" 한 줄 판단.
  - 〔문서: 실행 모드〕 · ↔ 책2 Ch9

- [ ] **메타 하네스: 6단계 파이프라인** — 하네스 자체를 설계하는 절차. 도메인 분석 → 팀 아키텍처 설계 → 에이전트/스킬 정의 → 오케스트레이션 → 검증 → 루프.
  - **왜 중요**: 새 유형의 반복 작업이 생겼을 때 즉흥 대신 6단계로 "전용 하네스"를 설계하면 재사용 자산이 된다.
  - **해보기**: 반복 작업 하나를 6단계에 대입해 한 문장씩 채우기.
  - **주의/핵심**: "파일이 없으면 존재하지 않는다" — 에이전트·스킬은 파일로 정의해야 재현됨. 메타스킬도 폭주할 수 있으니 안전장치 필요.
  - 〔문서: 하네스 설계 방법론〕 · ↔ 책2 Ch7

- [ ] **안티패턴 · 토큰 경제** — 자주 밟는 지뢰와 비용 관리.
  - **왜 중요**: 대군을 돌릴수록 토큰·시간이 크게 듦. 병목 튜닝하듯 낭비를 걷어내야 함.
    - 배리어 남용: `pipeline`이면 될 걸 `parallel`로 묶어 빠른 에이전트를 놀림.
    - 침묵 절단(silent cap): top-N만 보고 "다 봤다" 착각 → 무엇을 뺐는지 로그로.
    - 폭주: 무한 루프 방지(횟수·예산 상한).
    - 컨텍스트 넘침: 서브에이전트는 결과만 반환(파일 덤프 금지).
  - **해보기**: 처음 만든 워크플로에서 "이 단계가 정말 모두를 기다려야 하나?"를 점검해 배리어 하나 제거.
  - 〔문서: 안티패턴·토큰 예산〕 · ↔ 책2 부록 B/D

## Part 6. 실전 조합 레시피

> 위 Part 2~5를 실제로 엮는 방법. 게임서버 맥락의 일반 시나리오로 든다(특정 파일·경로 없이 구조만).

- [ ] **설정/파라미터 A/B 스윕 → 워크플로우 자동화** — 손으로 돌리던 설정별 실험·수집·판정을 Workflow로 팬아웃.
  - **레시피**: `pipeline(설정목록, 실험실행, 지표수집, 판정)`. 설정목록 = 스레드 수·배칭 on/off 같은 조합. 실험실행 = 해당 설정으로 부하 실행, 수집 = 지표 파싱, 판정 = 건강 기준(지연 임계·오버플로 0 등) 적용.
  - **payoff**: 스윕 전체를 무인으로 돌리고 판정표만 회수.
  - **주의**: 각 실험은 독립이라 배리어 불필요 → `pipeline` 기본. "최적 조합 선정"만 전체 결과가 필요하므로 그 단계만 모아서.
  - 〔연결: Part 5 Workflow·패턴〕

- [ ] **대규모 코드베이스 감사 → 병렬 서브에이전트 팀** — 많은 파일 감사를 영역으로 나눠 동시에, 지적은 반대심문으로 검증.
  - **레시피**: 팬아웃(네트워크·세션·로깅 등 영역별 탐색 에이전트) → 팬인(중복 지적 병합) → 생성-검증(각 지적을 "정말 결함인가" 반대심문, 과반 반박 시 폐기).
  - **payoff**: 넓게 훑되 할루시네이션 지적을 걸러냄. 진짜 결함만 남김.
  - **주의**: 검증 에이전트에 "근거(파일·라인) 없으면 폐기, 애매하면 결함 아님이 기본값" 명시 — 억지 지적 방지.
  - 〔연결: Part 3 서브에이전트, Part 5 생성-검증 패턴〕

- [ ] **반복 산출물 파이프라인 → 스킬로 고정** — 문서·리포트·도식처럼 절차가 정해진 산출물을 스킬/커맨드로 캡처.
  - **레시피**: 반복 절차(입력 로드 → 생성 → 검증 → 발행)를 커스텀 스킬 또는 `.claude/commands/`로. 검증 단계는 자동화(브라우저·사람에게 떠넘기지 말 것).
  - **payoff**: 매번 "처음부터"가 사라지고 절차가 일관됨.
  - **주의**: 과거에 밟은 함정(인코딩·클래스 충돌 등)을 스킬 지침에 박아두면 재발 방지.
  - 〔연결: Part 3 스킬·커스텀 명령〕

- [ ] **커밋 전 게이트 → 훅** — 리뷰·보안·빌드를 커밋 직전 자동.
  - **레시피**: 훅(또는 커밋 전 습관)으로 변경 diff에 `/code-review`·`/security-review`를 걸고, Release 빌드 통과까지 확인 후 커밋.
  - **payoff**: 경계 결함·회귀를 커밋 전에 차단.
  - **주의**: 훅은 하네스가 실행 → 지침이 아니라 훅으로 걸어야 강제됨(Part 4). 무거운 리뷰를 매 저장마다 돌리면 방해 → 커밋 시점 이벤트에만.
  - 〔연결: Part 2 리뷰·보안, Part 4 훅〕

## Part 7. 설정·권한 체계

설정 파일 계층·권한 규칙·CLAUDE.md 심화. 반복 프롬프트를 없애고 위험을 막는 토대.

- [ ] **settings.json 계층** — 여러 위치의 설정이 우선순위로 합쳐진다.
  - **왜 중요**: 같은 키를 여러 파일에 두면 예상과 다르게 동작. "허용했는데 왜 막히지?"는 대개 우선순위 문제.
  - **계층(높음→낮음)**: 관리 정책(조직 배포, 무시 불가) → 명령행 인수 → 로컬 `.claude/settings.local.json`(git 미추적) → 프로젝트 `.claude/settings.json`(공유) → 사용자 `~/.claude/settings.json`.
  - **주의/핵심**: 권한은 **deny → ask → allow** 순으로 평가 → deny가 항상 이긴다. 민감정보(키·로컬경로)는 `.local.json`이나 환경변수로.
  - 〔문서: Settings〕 · https://code.claude.com/docs/en/settings.md
- [ ] **권한 규칙 (allow / deny / ask)** — 도구 접근을 규칙으로 제어해 반복 프롬프트를 없애고 위험을 막는다.
  - **왜 중요**: 규칙이 없으면 도구마다 매번 승인. 반대로 너무 열면 위험 명령이 자동 실행.
  - **패턴 예**: `Bash(npm run *)`(접두만; 공백 위치 주의 — `Bash(npm*)`는 npx도 매칭) / `Read(src/**)`·`Edit(/docs/**)`(경로 글롭) / `WebFetch(domain:github.com)` / `mcp__<서버>__<도구>`.
  - **주의/핵심**: Bash 패턴은 보안 경계로는 약함(변형으로 우회) → 중요한 건 규칙 + 훅 조합. 권한 모드는 Part 1 참조.
  - 〔문서: Permissions〕 · https://code.claude.com/docs/en/permissions.md
- [ ] **CLAUDE.md 심화** — 매 세션 로드되는 지속 지침. 잘 쓰면 반복 실수를 줄이고, 크면 컨텍스트를 낭비한다.
  - **왜 중요**: "깔끔하게" 같은 모호한 지시는 무시되기 쉽고, "2칸 들여쓰기·타입 명시" 같은 구체 지시는 준수율이 높다.
  - **위치·범위**: `./CLAUDE.md`(프로젝트, 커밋) / `~/.claude/CLAUDE.md`(개인 전역) / 조직 정책 경로. 작업 디렉토리에 가까운 것이 우선.
  - **해보기**: `/init`로 초안 생성 후 다듬기. 목표 200행 이내. 주제는 `##` 헤더로 구분.
  - **주의/핵심**: `@경로`로 다른 파일 임포트, 경로별 규칙은 `.claude/rules/`(프론트매터 `paths`로 조건부 로드). CLAUDE.md는 "지침"이라 강제가 필요하면 훅(Part 4). 같은 주제로 2번 이상 교정하면 추가 신호.
  - 〔문서: Memory / CLAUDE.md〕 · https://code.claude.com/docs/en/memory.md
- [ ] **기타 설정** — 환경변수·상태줄·출력 스타일 등.
  - **왜 중요**: `NODE_ENV` 같은 상수를 매번 입력 않으려면 `env`에. 민감정보는 로컬/환경변수로.
  - **해보기**: `/config`로 현재 설정 확인. env·훅은 settings.json에.
  - **주의/핵심**: 상태줄·출력 스타일 세부는 버전·클라이언트(CLI/앱/웹)별로 다름 → 확인 필요.
  - 〔문서: Settings〕

**템플릿 · settings.json 권한 (유효 JSON — 실제 파일에 주석 불가)**
```json
{
  "permissions": {
    "defaultMode": "acceptEdits",
    "allow": ["Bash(npm run *)", "Bash(git status)", "Bash(git diff *)", "Read(src/**)", "WebFetch(domain:github.com)"],
    "ask": ["Bash(rm -rf *)", "Edit(.env*)"],
    "deny": ["Bash(git push *)", "Bash(git reset --hard)", "Read(/etc/**)"]
  },
  "env": { "NODE_ENV": "development" }
}
```
- **바꿀 곳**: 명령·경로·도메인을 네 프로젝트로. **함정**: deny가 allow보다 우선. 실제 settings.json은 주석 불가.

**템플릿 · CLAUDE.md 골격**
```markdown
# <프로젝트 이름>
한 줄 정의.

## 빌드·테스트
- 빌드: <명령> / 테스트: <명령>(커밋 전 필수) / 린트: <명령>

## 코딩 규칙
- 들여쓰기·따옴표·네이밍 등 구체 규칙

## 주의사항
- 커밋 금지 파일, 마이그레이션 리뷰 필수 등

## 참고
@<중요문서.md>
```
- **바꿀 곳**: 각 섹션을 네 규칙으로. **함정**: 발견 가능한 정보(디렉토리 나열 등)보다 함정·근거·관례를 담아야 값어치. 200행 넘으면 분리.

## Part 8. Git · PR · 병렬 작업

> 아래 명령·플래그는 2026-07 공식 문서 기준. 세부는 버전 따라 다르니 `/help`로 확인.

- [ ] **커밋 워크플로 & 안전 가드레일** — 커밋을 요청하면 변경을 요약해 메시지를 쓰고 적용한다. 단, 함부로 하지 않는다.
  - **왜 중요**: Claude Code는 **명시 요청 없이 커밋/푸시하지 않는다**. push·force-push·태그 등 외부 작업은 사용자 몫.
  - **해보기**: "이 변경 커밋해줘"(메시지 자동) 또는 메시지 지정. 커밋 전 검증은 훅(PreToolUse, `Bash(git commit*)`)으로.
  - **주의/핵심**: 셸 명령(`rm`·`mv` 등)은 체크포인트 미추적 → git으로 관리.
  - 〔문서: Common Workflows〕
- [ ] **리뷰: 내 diff vs GitHub PR** — 내 작업 검토는 `/code-review`, 남의 PR·공식 검토는 `/review`나 GitHub App.
  - **왜 중요**: 리뷰 플랫폼 구독 없이도 내 변경을 엄격히 검사 가능.
  - **해보기**: `/code-review high`(로컬), `--fix`(수정 적용), `--comment`(PR 인라인 코멘트). PR 자동 검토(GitHub App)는 Team/Enterprise 전용일 수 있음 → 확인.
  - 〔문서: Code Review〕
- [ ] **git worktree 병렬 작업** — 여러 작업을 격리된 작업트리에서 동시에, 파일 충돌 없이.
  - **왜 중요**: 기능 A 작업 중 버그 B를 같은 저장소·다른 브랜치에서 병행.
  - **해보기**: 여러 에이전트를 각자 worktree(백그라운드)에서 돌리고 한 화면에서 관리. 구체 플래그·명령명은 공식 worktree 문서로 확인.
  - **주의/핵심**: `.git`은 공유, 파일만 격리. 변경 있는 worktree는 자동 정리에서 보존. 각 에이전트가 독립 모델 호출 → 쿼터 소비.
  - 〔문서: Worktrees / Agent View〕
- [ ] **세션 재개·분기** — 다른 방향 시도는 분기, 며칠에 걸친 작업은 재개.
  - **왜 중요**: 대안 탐색 시 원본 보존, 긴 작업의 문맥 유지.
  - **해보기**: `claude -c`(최근 계속), `claude -r`(세션 선택 재개), `/branch`(현재 대화 복사해 분기). PR 기준 재개 옵션도 있음(확인).
  - 〔문서: Sessions〕
- [ ] **되돌리기 역할 분담** — `/rewind`는 Claude의 파일 편집만 추적. 나머지는 git.
  - **왜 중요**: 실수한 편집은 빠르게 되감되, 셸·서브에이전트 편집은 추적 밖.
  - **해보기**: `/rewind`로 코드/대화 복구. 셸로 바꾼 건 `git reflog`·`git reset`으로.
  - 〔문서: Checkpointing〕

## Part 9. 헤드리스 · 자동화

> 명령·플래그는 2026-07 공식 문서 기준. `/help`·문서로 확인.

- [ ] **헤드리스 실행 (`claude -p`)** — 비대화 1회 실행 후 종료. 스크립트·CI·훅에서 사용.
  - **왜 중요**: 사람 없이 파이프라인에서 클로드 코드를 호출.
  - **해보기**: `cat build.log | claude -p "에러 진단"`. `--output-format json`으로 구조화 출력(결과·비용·메타).
  - **주의/핵심**: 입력 크기 제한 있음 → 큰 데이터는 파일 참조. 종료 코드로 성공/실패 판정.

- [ ] **도구 자동승인** — 무인 실행 시 권한 프롬프트를 미리 처리.

  - **해보기**: `--allowedTools "Bash,Read,Edit"` 또는 `--permission-mode acceptEdits`.
  - **주의/핵심**: 무인 자동승인은 위험 범위를 좁게. deny 규칙은 그대로 적용.

- [ ] **CI 통합** — GitHub Actions·커밋 훅·스케줄 작업에서 에이전트 활용.
  - **왜 중요**: PR 검토·버그 수정·리포트 자동화.

  - **주의/핵심**: 비밀은 CI 시크릿으로(코드에 키 금지). 비용 = CI 분 + 토큰.

- [ ] **Agent SDK** — 클로드 코드를 프로그램에 에이전트로 임베드(Python/TypeScript).
  - **왜 중요**: 커스텀 앱·장시간 세션·프로그램 제어.
  - **해보기**: `@anthropic-ai/claude-agent-sdk`(TS) / `claude-agent-sdk`(Python). 내장 도구·훅·서브에이전트·MCP 지원.
  - **주의/핵심**: `ANTHROPIC_API_KEY` 필요. 정확한 패키지·API는 SDK 문서로 확인.
  - 〔문서: Agent SDK〕
- [ ] **모델 선택** — 작업 복잡도·속도·비용 균형.
  - **왜 중요**: 무거운 추론엔 상위 모델, 단순·대량엔 경량이 싸고 빠름.
  - **해보기**: 현역(2026-07): Fable 5·Opus 4.8(복잡 추론·에이전트) / Sonnet 5(균형) / Haiku 4.5(최속). 위로 갈수록 능력·비용↑. `/model <이름>`.
  - **주의/핵심**: 정확한 가격·한도는 플랫폼 가격 페이지로(수치는 자주 바뀜). 모델 ID는 고정 스냅샷.
  - 〔문서: 모델 개요 / Pricing〕
- [ ] **캐싱·컨텍스트로 비용 절감** — 프롬프트 캐시와 컨텍스트 관리.
  - **왜 중요**: 반복 쿼리·다중턴에서 운영비가 크게 준다.
  - **해보기**: 안정된 앞부분(시스템·CLAUDE.md·도구정의)은 캐시로 재사용. `/context`·`/compact`로 관리.
  - **주의/핵심**: 캐시 읽기는 싸고 쓰기는 프리미엄, 유효시간 짧음(수 분). 앞부분이 자주 바뀌면 캐시가 깨짐. (원리는 Part 10)
  - 〔문서: Prompt caching / Headless〕

## Part 10. LLM 작동 원리 (사용에 필요한 만큼)

> 클로드 코드를 "왜 이렇게 써야 하나"가 여기서 나온다. 비공개 아키텍처 세부가 아니라, 실사용에 직결되는 원리만.

- [ ] **토큰과 토크나이저** — 모델은 글자가 아니라 토큰(단어 조각) 단위로 읽고 쓴다.
  - **핵심**: 입력·출력·비용·컨텍스트 한도가 모두 토큰으로 계산. 한글은 영어보다 토큰을 더 먹는 편.
  - **그래서**: 긴 로그·파일을 통째로 붙이면 토큰이 훅 는다 → 필요한 부분만(@범위·발췌). 비용·속도가 토큰에 비례.
- [ ] **컨텍스트 창과 어텐션** — 모델은 "지금 창에 든 토큰"만 본다. 어텐션으로 토큰끼리 관계를 계산하는데, 창이 길수록 흐려지고 느려진다.
  - **핵심**: 창을 꽉 채울수록 중간 내용이 묻히고 품질·속도가 떨어질 수 있다.
  - **그래서**: `/clear`·`/compact`로 무관한 내용 비우기, 중요한 지시는 앞이나 최근에, 큰 작업은 서브에이전트로 쪼개 각자 작은 창에서.
- [ ] **다음 토큰 예측(자기회귀)** — 모델은 "다음에 올 가장 그럴듯한 토큰"을 하나씩 이어붙인다. 사실 검증기가 아니라 확률적 문장 생성기.
  - **핵심**: 그래서 **자신 있게 틀릴 수 있다**(할루시네이션). 그럴듯함 ≠ 사실.
  - **그래서**: 근거(파일·라인) 요구, 검증 에이전트로 반대심문(Part 5), 중요한 명령·API는 공식 문서로 확인.
- [ ] **학습 방식(사전학습 + 정렬)** — 대량 텍스트로 다음 토큰 예측을 배우고, 사람 선호로 다듬는다(RLHF 등). 지식은 **학습 시점(cutoff)** 까지.
  - **핵심**: cutoff 이후 정보·최신 API 변경은 모른다.
  - **그래서**: 최신 라이브러리·명령은 문서/웹으로 보강. 이 가이드가 "공식 문서가 정본"인 이유.
- [ ] **호출마다 상태 없음(stateless)** — 모델은 매 호출에 창에 든 것만 보고, 지난 대화를 스스로 기억하지 않는다. 이어져 보이는 건 매번 다시 넣어주기 때문.
  - **핵심**: 세션이 바뀌면 백지. "기억"은 도구가 주입하는 것.
  - **그래서**: `CLAUDE.md`·메모리·계획 파일이 필요(Part 0·7). "앞으로 매번 X"는 훅·파일로 고정해야 함(Part 4).
- [ ] **프롬프트 캐시** — 창 앞부분이 그대로면 그 계산을 재사용해 더 싸고 빠르게(유효시간 짧음, 예: 수 분).
  - **핵심**: 안정된 앞부분은 캐시로 이득, 자주 바뀌면 캐시가 깨진다.
  - **그래서**: 오래 쉬었다 다시 시작하면 캐시가 만료돼 느려질 수 있음. 반복 작업은 텀 없이 이어가면 이득.
- [ ] **도구 호출(function calling)** — 모델은 직접 실행하지 못하고, "이 도구를 이렇게 부르겠다"는 구조화된 출력을 내면 하네스가 실행해 결과를 창에 넣어준다.
  - **핵심**: 파일 읽기·셸·검색이 다 이 방식. 모델↔하네스 왕복.
  - **그래서**: 도구 결과가 창을 먹는다(큰 출력=토큰 폭증) → 서브에이전트는 "결과만 반환"으로 보호(Part 5). MCP·훅도 이 왕복 위에.
- [ ] **온도·확장 사고** — 생성의 무작위성(temperature)과 사고를 길게 하는 모드가 답의 다양성·깊이를 바꾼다.
  - **핵심**: 어려운 추론엔 사고를 길게, 단순 작업엔 짧게가 효율적.
  - **그래서**: 가벼운 작업은 `/fast`로 빠르게, 복잡한 설계·디버깅은 사고 여유를 두기(Part 1).

## 부록 A. 템플릿 모음 (복붙용)

> 필드·문법은 2026-07 기준. 정확한 최신 스펙은 공식 문서(skills·subagents·hooks)로 확인. 전부 일반형 — `<...>` 부분을 네 것으로 갈아끼운다.

### 템플릿 · 커스텀 슬래시 명령
- **용도**: 자주 쓰는 지시를 `/이름`으로. **위치**: `.claude/commands/<이름>.md`(파일명이 명령명)
```markdown
---
description: 이 명령이 무엇을 하는지 한 줄
argument-hint: [인자]
---
$ARGUMENTS 로 받은 입력으로 작업.
1. ...
2. ...
```
- **바꿀 곳**: description(자동 매칭 기준)·본문. **함정**: 인자 치환 문법(`$ARGUMENTS`/`$1` 등)은 버전 따라 다를 수 있음 → 확인.

### 템플릿 · 스킬(Skill)
- **용도**: 다단계 절차·자동 호출. **위치**: `.claude/skills/<이름>/SKILL.md`
```markdown
---
name: <이름>
description: 언제 쓸지 명확히(자동 매칭 기준)
allowed-tools: Read, Grep, Bash
---
## 지시
1. ...
2. ...
```
- **바꿀 곳**: description·allowed-tools·본문. **함정**: 긴 참고자료는 별도 md로 분리(컨텍스트 절감). 추가 프론트매터 필드는 문서로 확인.

### 템플릿 · 서브에이전트
- **용도**: 독립 컨텍스트로 특화 작업. **위치**: `.claude/agents/<이름>.md`
```markdown
---
name: <이름>
description: 이 에이전트의 역할(위임 기준)
tools: Read, Grep
---
이 에이전트가 받을 지시(구체적으로).
```
- **바꿀 곳**: description·tools·본문. **함정**: 독립 컨텍스트라 필요한 맥락을 본문/호출에 직접. 도구는 최소로 제한.

### 템플릿 · 훅(hook)
- **용도**: 이벤트에 자동 실행(차단·포매팅·빌드). **위치**: `.claude/settings.json`의 `hooks`
```json
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "<빌드/포맷 명령>" }] }
    ],
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "<검사 스크립트>" }] }
    ]
  }
}
```
- **바꿀 곳**: 이벤트·matcher·command. **함정**: 훅은 stdin으로 JSON을 받음(도구 입력 등). PreToolUse는 종료코드 2로 차단(사유는 stderr). 대표 이벤트: PreToolUse·PostToolUse·UserPromptSubmit·Stop·SessionStart 등(전체·정확한 스키마는 공식 hooks 문서).

### 템플릿 · 설정 A/B 스윕 (Workflow)
- **용도**: 설정 조합마다 부하 실험→지표→판정을 무인 반복.
```js
export const meta = { name:'ab-sweep', description:'설정 조합 A/B 부하 스윕', phases:[{title:'run'}] };
const CONFIGS = [ /* {threads:4, batch:true} ... 조합들 */ ];
const rows = await pipeline(CONFIGS,
  cfg => agent(`<cfg 적용 → 부하 실행 → 지표 파싱해 반환>`,
               { schema: METRICS_SCHEMA, label:`run:${cfg.threads}`, phase:'run' }),
  (m, cfg) => ({ ...cfg, ...m, ok: m.p99 < LIMIT && m.overflow === 0 }));
return rows;
```
- **바꿀 곳**: `CONFIGS`·실행부·판정 기준·`METRICS_SCHEMA`. **함정**: 단계 사이 배리어 불필요 → `pipeline`. 실제 부하는 무거움. Workflow는 명시 요청해야 켜짐.

### 템플릿 · 대규모 감사 (팬아웃 → 반대심문 검증, Workflow)
- **용도**: 많은 영역을 동시에 감사하고, 각 지적을 검증으로 걸러 진짜 결함만.
```js
const AREAS = ['네트워크','세션','로깅'];
const found = (await parallel(AREAS.map(a => () =>
  agent(`${a} 영역만 감사. 지적은 파일·라인 근거 포함.`, {schema: FINDINGS, phase:'find'}))))
  .filter(Boolean).flatMap(r => r.items);
const verified = await parallel(found.map(f => () =>
  agent(`이 지적이 진짜 결함인지 반대심문. 근거 없으면 폐기, 애매하면 결함 아님.`,
        {schema: VERDICT, phase:'verify'}).then(v => ({...f, real: v.real}))));
return verified.filter(x => x.real);
```
- **바꿀 곳**: `AREAS`·스키마. **함정**: "애매하면 결함 아님 기본값" 명시(억지 지적 방지). 팬아웃은 배리어(`parallel`)로 모아 중복 제거 후 검증.
